# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Console app (.NET 10, C#) that runs a market-making "spread" bot on any exchange [CCXT](https://github.com/ccxt/ccxt) supports with websockets (official `ccxt` NuGet package, `ccxt.pro` streams); the first target is Binance spot (`ExchangeId`, `UseSandbox` for its testnet). It scans markets for wide bid/ask spreads, allocates a slice of quote-currency balance to a `Bot` per market, buys at bid + 1 tick and sells at ask − 1 tick with post-only orders.

## Commands

```sh
dotnet build SpreadBot.sln
dotnet test SpreadBot.sln
dotnet test SpreadBot.Tests --filter "FullyQualifiedName~BasicBotFlowTest"   # single test
dotnet run --project SpreadBot -- C:\absolute\path\to\appsettings.json
dotnet publish SpreadBot -p:PublishProfile=FolderProfile                      # self-contained, single-file, linux-x64 (untrimmed)
dotnet dotnet-ef migrations add <Name> --project SpreadBot --output-dir Infrastructure/Persistence/Migrations   # after changing the schema (local tool: dotnet tool restore)
```

- Tests are MSTest 4 + Moq. Besides the end-to-end `BasicBotFlowTest` (`UnitTest1.cs`), tests pin config binding (culture, defaults, hot-reload), the CCXT → model mapping (`CcxtMappingTests`: orders, fees by currency, statuses, exception → `ApiErrorType`), and persistence (`SqliteCoordinatorContextTests`, against in-memory SQLite databases, which the user allowed; never a real database file). `Migrations_MatchTheModel` fails when the model changes without a migration. Nothing talks to a real exchange; `MockExchange` captures the stream callbacks so tests push updates.
- The build is warning-free; keep it that way: `dotnet build SpreadBot.sln --no-incremental -warnaserror`.
- No linter/formatter config exists.

## Runtime files and config

- **Settings path**: first CLI arg (default `appsettings.json`), resolved with `ToLocalFilePath()` = relative to the *executable's* directory, not the cwd. `appsettings.json` is `CopyToOutputDirectory=Never`, and under `dotnet SpreadBot.dll` the "executable" is `dotnet.exe` — so pass an absolute path.
- `appsettings.json` is tracked in git. Never put real credentials in it; use a separate untracked file passed as the arg.
- Only properties declared on `AppSettings` / `SpreadConfiguration` bind; unknown keys are silently ignored. `BlacklistedMarkets` must be a list: `AppSettings.FromConfiguration` refuses a single string at startup, which the binder would skip (a reload with one fails in Newtonsoft and keeps the old settings). `MinimumPrice` / `MinimumNegotiatedAmount` live inside each `SpreadConfiguration`. The checked-in `appsettings.json` targets the Binance testnet with empty keys.
- Settings hot-reload via `FileSystemWatcher`, but `AppSettings.Reload` only applies `MaxNumberOfBots`, `MaxNumberOfBotsPerMarket`, `BlacklistedMarkets` and `SpreadConfigurations`, then raises `Reloaded` (Coordinator regroups configs by base market). A file without `SpreadConfigurations`, or with one lacking its `BaseMarket`, is refused before anything is applied.
- Files the bot writes/reads at runtime:
  - The SQLite database (`DatabasePath`, default `spreadbot.db`, relative to the **settings file**), written by `SqliteCoordinatorContext`. The bot applies pending EF Core migrations at startup, copying an existing file to `<path>.before-<migration>.bak` first. Tables: `Configurations` (one row per configuration, by its equality), `Bots` (active ones are resumed when `TryToRestoreSession` is true; finished ones keep `FinishedAt` and `Profit` = balance − allocation), `Orders` (append-only: every state a bot applies, including closed orders it books) and `Dust`.
  - `dashboard-secrets.json` — next to the settings file, created on the dashboard's first start (git-ignored): its access token and Web Push (VAPID) keys.
  - `telegramSettings.json` — exe-dir, optional (`ChatId`, `BotToken`, `ChangeThresholdPerMarket`); if present, `BalanceReporter` posts balance changes to Telegram.

## Architecture

Wiring is manual in `Program.cs` (no DI container): `CcxtExchange` → `DataRepository` → `Coordinator` (with `SqliteCoordinatorContext`).

**Data flow (`Infrastructure/DataRepository.cs`)** — the hub everything subscribes to.
- Exchange stream callbacks (`OnBalance/OnMarketData/OnOrder`) push into one `BlockingCollection` per stream; each is drained by its own background task, which merges into the `BalancesData` / `MarketsData` / `OrdersData` caches and invokes subscribers **synchronously on that consumer thread**. There are no sequence checks: stream and resync updates apply in arrival order.
- Market updates are partial (tickers vs. market metadata such as `PriceTick`/status); `MergeMarketData` null-coalesces field by field. A new `MarketData` field must be added there or it gets dropped on merge.
- A closed order is final: a late OPEN update for it is ignored.
- A REST resync — every `ResyncIntervalMs`, or once a stream that failed has re-subscribed (`OnStreamInterrupted`) — pauses all consumers (`ManualResetEvent`), refetches balances, markets (reloaded at most hourly, so halts and filter changes show up), tickers and open orders, and fetches each order a bot is tracking that the exchange no longer lists as open (it filled or was cancelled while the stream was down). Only one runs at a time; requests made while one runs get one more run after it (`pendingResyncs` counts them in `RequestResync`). Tracking is by subscription: `SubscribeToOrderData` takes the order (id + symbol), so a bot's order is fetchable even if no update for it ever arrived. Open orders no bot tracks are logged as errors.
- Consumer loops run on dedicated threads (`TaskCreationOptions.LongRunning`); don't start blocking loops with `Task.Run`, they pin thread-pool threads.
- Subscriptions are keyed by `Guid` per handler (market symbol / currency / client order id). Subscribing fires the callback immediately if cached data exists.

**Coordinator (`Logic/Coordinator.cs`)** — subscribes to all market deltas; for each viable market (not in `BlacklistedMarkets`, which names coins or `BASE/QUOTE` markets in any case, an entry naming no coin or market traded against a configured base market being logged as an error at startup and on reload, as a possible typo; online, no notice, with a price tick; sorted by `GetMarketComparer`) and each `SpreadConfiguration` for that base market, checks price/quote (a bid and an ask)/spread/volume/pump/tokenized-security filters and available balance, then creates a `Bot` with `AllocatedAmountOfBaseCurrency`, at most `MaxNumberOfBotsPerMarket` (default 1) per market across all configurations; a restored session keeps the bots it had. A restored bot whose market isn't in the market data would never get an update: if its base market is configured (so its markets were loaded) the exchange no longer lists it, and the bot is finished (`Bot.RequestFinish`), unless it has an open or UNKNOWN order: ccxt refuses every request on a market it doesn't list, so the order can't be cancelled or looked up, and the bot stays, holding its allocation and slot, while an unexpected error names the order. If its base market isn't configured, an unexpected error says so. Evaluation, allocation and unallocation are serialized by one lock (summaries and tickers arrive on different threads). On unallocation it records leftover held coins as "dust" for that market, which the next bot on that market inherits, capped at the coins no other bot claims minus the dust recorded on the coin's other markets; recorded dust beyond that isn't on the exchange and is dropped.

**Operator controls** (what the dashboard drives): `Coordinator.SetAllocationPaused` stops new allocations while running bots carry on; `Coordinator.FinishBot` runs `Bot.RequestFinish`, which cancels the bot's open order (retrying for 15 s; an order whose placement is unknown keeps it running) and finishes it as usual, market-selling what it holds; `Coordinator.WhyNotAllocatable` names the first filter a market fails for a configuration (`MarketFilters`, the same filters allocation uses), or the per-market cap if another configuration's bots fill it; `DataRepository.RequestResync` is public, and the repository records when each stream last delivered and the resyncs. `Logger.Logged` reports each written log on the logger's thread.

**Halt (`Coordinator.Halt`)** — the global stop for errors no retry fixes. `IExchange.OnFatalError` (raised by `CcxtExchange` whenever an error maps to `Unauthorized`: invalid or revoked keys, missing permissions, suspended account, `RestrictedLocation`, `ManualInteractionNeeded`, from a request or a stream) halts the Coordinator: it allocates nothing more, and each bot's `Bot.Halt` stops it trading (market data is ignored, `FinishWork` sells no dust) and cancels its open order, booking any fills (a failed cancel is retried, 3 s apart, for 30 s unless the account is refused, so the last one, up to three requests, answers within `HaltTimeout`; an order whose placement is unknown is logged and left to the next session). Bots keep their state and allocation, so the saved session resumes them; one the booking leaves with nothing to trade finishes as usual, its coins recorded as dust. The save on exit is bounded (30 s). `Coordinator.Halted` completes once the bots are done, including any a restore in progress allocates (at most `HaltTimeout`, 60 s); `Program` then saves the context (`ICoordinatorContext.Save`), flushes the log and exits with code 1. Enter exits the same way with code 0. Binance's per-symbol refusals ("This symbol is restricted/not permitted for this account", ccxt `PermissionDenied`) aren't fatal: they map to `MarketOffline`, and the adapter reports that market `Offline` from then on, so no bot is allocated on it again.

**BalanceLedger (`Logic/BalanceLedger.cs`)** — the only place that decides how much money is free. Exchange balances (`BalanceData.Amount` = Available, `Total`) are the source of truth; bots' `Balance`/`HeldAmount` say which part is theirs. **The exchange account is assumed to be dedicated to the bot** (the user's decision): every coin no bot claims counts as free, so it can be allocated, inherited as dust, or market-sold by a finishing bot. Don't run it on an account that also holds coins the bot must not touch. It keys on each bot's order (`CurrentOrderData`), not `BotState`: funds locked in an open order aren't in Available, and an open order's partial fills (bought coins, sell proceeds) are already in Available before the bot books them on close — so `Bot.ProcessOrderData` keeps `CurrentOrderData` updated on every OPEN update. Balances can run ahead of the bot's view, so it uses the newer of `CurrentOrderData` and `DataRepository.OrdersData` (an order the exchange reports closed counts as booked), and while `Bot.OrderRequestInFlight` it treats the order's locked funds as possibly unlocked (a cancel frees them before the bot sees the answer; a failed request keeps the flag set until the order's state is next applied). A currency is claimed both as a base market (bots' funds) and as a traded coin (bots' coins), e.g. BTC with BTC and USDT bases. Used for allocation, inherited dust, balance reporting, and a bot's reconcile after a rejected sell.

**Bot (`Logic/Bot.cs`)** — one per allocated market, state in `BotContext` (`Buying → BuyOrderActive → Bought → SellOrderActive → … → FinishedWork`).
- `ProcessMessage` is `async void` and serialized per bot by `BotContext.Semaphore` (FIFO `SemaphoreQueue`); a 1-minute timer logs if processing hangs. Market data is latest-wins: a message that is no longer the market's `MarketsData` entry (overtaken while it waited for the semaphore), or the entry already processed, is skipped (order data never is). Every update replaces the entry before reaching handlers, so the final entry is always acted on.
- Market data goes to the strategy; **order-state transitions live in `Bot.ProcessOrderData`** (OPEN → `*OrderActive`; CLOSED → update balance/held amount, then `Bought` / `Buying` / `FinishWork` depending on `MinimumNegotiatedAmount`).
- An order whose placement is unknown (`OrderStateUnknownException`) becomes the current order with status `UNKNOWN`, keyed by its client order id. While it is current, market data skips the strategy, so nothing else is placed; `ResolveUnknownOrder` looks it up via `GetOrderByClientId` at most every 5 s. Found → adopted as a normal current order (stream/resync updates with that client id adopt it too, in `ProcessOrderData`); only a report with an id and an OPEN/CLOSED status settles it (`ShowsOrderState`), anything less keeps it UNKNOWN. When the lookup answers `OrderNotOpen`, a stream report of it already in `DataRepository.OrdersData` (queued behind the lookup) counts as found: one that settles it is adopted, any other keeps it UNKNOWN, since the order exists. Otherwise, confirmed absent more than `IExchange.OrderRequestLifetime` after sending (ccxt's `recvWindow` + 50 s, so 60 s on Binance) → dropped, and the strategy places again. Any other lookup error keeps it UNKNOWN and never reaches `HandleApiException`, whose arms are about failed placements. `BalanceLedger` keeps the bot's funds claimed and also claims the most the order could have brought in already: a sell's `Quantity × Limit`, a buy's `Quantity`.
- `ApiException`s are handled per `ApiErrorType` in `HandleApiException`; `Unauthorized` only logs there, since the exchange's fatal error halts every bot. CCXT exception → `ApiErrorType` mapping is `CcxtExchange.ToApiException`; order the arms most-specific first (e.g. `RateLimitExceeded` derives from `NetworkError` in this ccxt version, not `DDoSProtection`).
- `FinishWork` is idempotent: it unsubscribes, market-sells leftover holdings if worth more than `2 × FeeRate × MinimumNegotiatedAmount`, calls back to the Coordinator to unallocate, and records profit; each step runs even if an earlier one fails. Messages queued behind it see `FinishedWork` and return.
- `Start` and `ProcessMessage` are `async void` entry points: keep all their work inside the `Task`-returning `StartAsync` / `ProcessMessageAsync`, which sit behind a catch-all — anything escaping an `async void` terminates the process.
- A sell rejected with `INSUFFICIENT_FUNDS` reconciles `HeldAmount` against a fresh REST balance (minus other bots' coins): within 2% it sells what's there; beyond that it retries, since the coins may not be settled yet. After 3 consecutive rejections it finishes, market-selling only what the exchange shows (`FinishWork(maxCoinsToSell)`); the rest stays held and is recorded as dust.

**Strategies (`Logic/BotStrategies`)** — each `SpreadConfiguration.Strategy` (`BotStrategyType`, saved by name; default `Spread`) picks what `BotStrategiesFactory` builds, one instance per bot. Strategies only react to market data and place/cancel orders through the `executeOrderFunction` callback (which updates `CurrentOrderData` and feeds the result back into `ProcessOrderData`).
- `SpreadStrategy` dispatches on `BotState` to an `IBotStateStrategy` (`Spread*StateStrategy`). Its buy states re-check the allocation filters on every market update (`MarketFilters.BuyingRejection`): a Buying bot whose market fails one finishes, and one with a resting buy cancels it first. The entry filters (minimum price and volume, tokenized securities) are left out, since a market drifting around one would make the bot leave and get allocated again on every trade; what is re-checked is the blacklist, notice, status, tick, the pump filter and the quote. Until the market shows a bid or an ask its quote (both sides, spread) isn't judged, since the filters reject a market without both; a one-sided quote is, which leaves it. While its market is offline a bot with a resting buy sends nothing (the exchange refuses requests there, e.g. on a symbol restricted for the account) and logs that once per buy; the buy rests until it fills or the exchange cancels it. Status only comes back Online with a markets reload (at most hourly), and a symbol restricted for the account never does. While its buy is the best bid, the spread is judged with the bid one tick lower, the one it improved on: on the ticker's own spread a market at the minimum would have it cancel and place the same buy again on every update. That gives a resting buy one tick of slack. A bot holding coins sells as usual and leaves once it is back in Buying. Its sell states take an `ISellFloor`, the lowest price the bot may ask (null: any). `BreakEvenSellFloor` (`Spread`): until `MinutesForLoss` has elapsed since the buy filled, break-even after fees (`BotContext.BreakEvenPrice`: `BoughtPrice / (1 − FeeRate)²`, assuming both the buy and the sell pay `FeeRate` and the buy's fee comes out of the coins). `DecayingSellFloor` (`PatientSpread`): starts `MinimumSpreadPercentage` above break-even and falls to it linearly over `MinutesForLoss`.
- `CalmSpreadStrategy` (`CalmSpread`) wraps a `SpreadStrategy` and bids only while the market's mid price has moved less than `MinimumSpreadPercentage` over the last `CalmSpreadStrategy.Window` (5 min), watched by the bot for at least that long (in memory: a restart waits again). Not calm, it holds off instead of finishing and cancels a resting buy, but a market failing the buy states' filters (with their one tick of slack) is still left, and one without a quote yet goes to the wrapped strategy, which waits; selling is never held back.
- Two configurations on the same base market compete for its markets. With `MaxNumberOfBotsPerMarket` 1 the first one in the settings takes every market it can afford and the next only gets the rest; above 1 they allocate bots on the same markets, where they outbid each other. Compare strategies on different base markets.

**Exchange abstraction (`Infrastructure/Exchanges`)** — `IExchange` uses only the app's models (`MarketData`, `OrderData`, `BalanceData`); symbols are CCXT's `BASE/QUOTE` (SpreadBot calls the quote currency the "base market": BTC in `NMR/BTC`). Orders are addressed by `(id, symbol)` because many exchanges require the symbol. `CcxtExchange` holds the base `ccxt.Exchange` built from `ccxt.pro.{ExchangeId}`; its watch loops reconnect with a delay and raise `OnStreamInterrupted` on recovery: after the first update, or after `ResubscribeGrace` (2 s) if none came (then again on the first update), since the order and balance streams may stay silent for long. `GetMarkets` reloads ccxt's markets (Binance: spot only) at most once per `MarketsReloadInterval` (1 h; 5 min after a failed one), since ccxt's own requests await a load in progress (resyncs fetch markets first for that reason, before pausing the consumers), and returns the quote currencies' spot markets, inactive ones and ones the reload no longer lists as `Offline`; the tickers watch the active ones. A failed or empty reload keeps the previous markets and puts ccxt's last good `marketsLoading` (and, via `setMarkets`, its markets) back, since ccxt awaits it before most requests. ccxt.pro Binance resets its balance cache on every new websocket client, so the balance stream never re-sends values from before an outage. Limit orders are post-only (a spread bot must never take). Every order gets a fresh client order id. If the create's answer doesn't show the order's state (any `ccxt.OperationFailed` except `RateLimitExceeded` / `DDoSProtection` / `InvalidNonce`, which refuse the request itself; that covers network errors, unreadable responses and Binance's -1000/-1001/-1006 "execution status unknown" codes; any non-ccxt exception, since ccxt's C# `fetch` wraps only `HttpRequestException`/`WebException`/`HttpListenerException` and lets a timeout's `TaskCanceledException` or an `IOException` escape raw; an ack without status or id; or an ack the adapter fails to map), the adapter throws `OrderStateUnknownException` carrying the order as sent (`OrderStatus.UNKNOWN`, no id) instead of a retryable error, so a retry never duplicates an accepted order. Other calls map a raw timeout/`IOException` to `RetryLater`. ccxt's C# client (4.5.94) never applies its `timeout` option, so the adapter sets `httpClient.Timeout` from it (ccxt's default is 10 s; HttpClient's would be 100 s). A cancel re-fetches the order, so a cancel that races a fill reports the real final state. Fees are split by currency: `Commission` (quote) and `CoinCommission` (taken from the coin, e.g. Binance buys without BNB), and `HeldAmount` is booked net of `CoinCommission`. Binance's REST order endpoints carry no commission (the stream accumulates it per order), so `GetOrder`/`GetOrderByClientId` take a closed, filled order's fees from `FetchOrderTrades`; until the trades cover the fill they throw `RetryLater` rather than let the close be booked without fees.

**Persistence (`Infrastructure/Persistence`)** — `SqliteCoordinatorContext` (behind `ICoordinatorContext`) keeps the allocated bots and dust in memory, where the Coordinator reads them, and writes behind to SQLite on one writer thread:
- a bot row when a bot is added (its orders reference it; adding reopens a row a snapshot closed during a restore) or removed (with `FinishedAt` and `Profit`);
- every order state, from `Bot.OrderUpdated`, deduplicated per client order id;
- a snapshot of every bot (each under its own semaphore, debounced 1 s on `ContextChanged`) that also syncs the dust and closes the open rows of bots no longer allocated (a previous session's that weren't resumed), so the stored session is always the current one, as the old session file was.

A restored bot keeps its `Guid`. Its current order is exactly the `Orders` row its bot row points to (`CurrentOrderRecordId`, a foreign key, so the database can't hold a bot naming an order it doesn't have). Every bot write links an equal stored state, appending one if none exists, so a restore never guesses. Each write batch is one transaction, including the saves it makes midway (a new configuration; a new bot before its order, since each references the other). Snapshots never store a `FinishedWork` bot, so the Coordinator's "saved while finishing" restore branch isn't reached with this context; `RemoveBot` on a stored bot that isn't allocated would close it from its stored values. After `Dispose`, nothing more is written.

**Dashboard (`Dashboard/`)** — opt-in (`Dashboard.Enabled`): Kestrel inside the bot (`FrameworkReference Microsoft.AspNetCore.App`), bound to `Dashboard.Url` (`127.0.0.1:5080`; a non-loopback address is refused, since the token would travel in plain HTTP). The user reaches it from a phone through `tailscale serve`, which adds the HTTPS that installing the PWA and Web Push need; `Dashboard.PublicUrl` is that HTTPS address (the push sender, and where notifications link). It's started from `Program` after the Coordinator; if it can't start, the bot runs without it.
- `DashboardHost` serves the PWA (`Dashboard/wwwroot`, embedded resources so the single-file publish carries it; vanilla JS, no build step) and the API. Every `/api` call needs `Authorization: Bearer <AccessToken>` (constant-time compare). Actions need a typed confirmation: `HALT`, or the bot's market symbol to finish it. Security headers include a strict CSP. System.Text.Json (camelCase, enums as strings) with the records in `DashboardModels.cs`, not Newtonsoft.
- `DashboardService` reads live state (bots, `BalanceLedger` totals, stream activity, configurations, dust) and history from SQLite (read-only queries on short-lived contexts; SQLite can't sum decimals, so finished bots are aggregated in memory, and the result is cached for 60 s or until a bot finishes).
- `/api/stream` is server-sent events read with fetch (EventSource can't send the token). `LiveFeed` fans out to bounded per-connection queues that drop the oldest events.
- `ActivityMonitor` (every 2 s) publishes the state to open dashboards and turns the database's append-only records into fills and finished bots (no hook in the bots). It also logs `Logger.Logged` entries, pushes unexpected errors (at most one per 10 min, then a count), flags prices stopping for 2 min, and samples equity every 5 min into `EquitySnapshots`. On a halt, `Program` awaits `AnnounceHalt` (up to 10 s) before exiting, so the halt push goes out.
- `PushNotifier` sends Web Push (`WebPush` NuGet) to `PushSubscriptions`, each with its chosen categories (halt, finished, fills, errors, streams). Only the browsers' push services are accepted as endpoints (https, port 443, no userinfo), since the bot POSTs to them, and at most 20 devices. Sends go one at a time from a bounded queue, with a 10 s timeout. A full queue refuses new messages, and the halt skips the queue (`NotifyNow`). A subscription is dropped on 404/410, or after 3 refusals (401/403) in a row: one may be the bot's own key or clock. Push failures are logged as errors, never unexpected ones, which would push themselves.

**Singletons with background consumers** — `Logger`, `BalanceReporter` each own a `BlockingCollection` drained by a background task. Use `Logger.Instance.LogMessage / LogError / LogUnexpectedError`, not `Console`.

## Gotchas

- `SpreadConfiguration` overrides `Equals`/`GetHashCode` over its value fields (all but `AvoidTokenizedSecurities`) and is used as a dictionary key (`Coordinator.AllocatedMarketsPerSpreadConfiguration`) and to find its `Configurations` row (`SqliteCoordinatorContext` caches rows by it; EF maps `SpreadConfiguration` itself, with a shadow key). Editing a config's values makes it a *different* configuration, so its bots and profit are tracked under a new row. A new field must join both `Equals` and `GetHashCode` and the unique index in `SpreadBotDbContext`, and needs a migration.
- Serialization is Newtonsoft.Json everywhere. Use Newtonsoft attributes; `System.Text.Json` attributes are silently ignored.
- Trimming is off on purpose: Newtonsoft, the config binder and CCXT need reflection (`CcxtExchange` creates the exchange class by name). Don't re-enable `PublishTrimmed`.
- Don't enable `ImplicitUsings`: several files use `System.Timers.Timer`, which would clash with `System.Threading.Timer`.
- Telegram.Bot is pinned on 15.x. CCXT's C# models use `double`; convert to `decimal` at the adapter boundary (`CcxtExchange.ToDecimal`) and never let doubles into the bot's accounting.
- A `BotContext` member that must survive a restart needs a `BotRow` column (plus `SqliteCoordinatorContext.ToRow`/`ToBotContext`) and a migration. `OrderData` is stored as is in `Orders` (EF maps the class; its `Id` is the `ExchangeOrderId` column), so a new `OrderData` property is a new column. Enums are stored by name and dates as UTC.
- Prices are `decimal`; move prices by `MarketData.PriceTick` (from CCXT market precision) and round with `CeilToTick`. `Setup` rejects an exchange whose ccxt precision mode is significant digits, which has no fixed tick. A market without a tick isn't quoted. On a one-tick spread the strategies join the bid/ask instead of improving it, since crossing would get the post-only order rejected. Amounts are left to CCXT, which truncates them to the market's step size.
